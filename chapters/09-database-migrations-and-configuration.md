## What I am learning here

Application configuration changes between a developer machine, a test environment, and production. External properties let the same application artifact run with different database locations and credentials. Schema migrations record database structure changes in order so each environment can be upgraded consistently.

## Keep local connection settings external

~~~properties
spring.datasource.url=jdbc:postgresql://localhost:5432/catalog
spring.datasource.username=catalog_app
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true
~~~

Provide the real username and password outside the repository through environment configuration or a secret store. Do not commit production credentials. Use a local profile or container when a developer needs an isolated database.

For production, prefer versioned migrations over automatic schema creation. A Flyway migration can create the initial table:

~~~sql
CREATE TABLE book (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL
);
~~~

Place the file at src/main/resources/db/migration/V1__create_book.sql. Later schema changes get a new versioned migration rather than rewriting one already applied. Set Hibernate to validate the schema when the application starts so a mismatch is visible without letting the application silently alter production tables.

Use Spring Boot's configuration property sources consistently. Keep defaults safe for local development and give each environment a documented way to supply its database URL and credentials.
